# Разработка и проверки

```bash
npm ci
npm run check
npm audit --audit-level=high
npm pack --dry-run
```

`npm run check` последовательно запускает lint, проверку типов исходников и тестов, тесты и сборку. `npm run lint` использует [Oxlint](https://oxc.rs/docs/guide/usage/linter.html) с проверками correctness; предупреждения также завершают команду с ошибкой. Каждый этап можно запустить отдельно: `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`.

`npm test` компилирует тесты и исходники в `.test-dist`, затем запускает встроенный `node:test`. CLI-тесты используют скомпилированную тестовую точку входа; тест npm-архива отдельно собирает `dist` через `prepack`.

Для интеграционных тестов нужен `openssl` с поддержкой `req -addext` в PATH. Они генерируют временные сертификаты, доверяют им через `NODE_EXTRA_CA_CERTS` только в тестовых дочерних процессах и не отключают TLS-проверку. Тест упаковки выполняет `npm install` во временном каталоге: ему может понадобиться доступ к npm registry. Временные каталоги и ключи удаляются при завершении тестов.

Проверены на POSIX-среде с Node.js 24. Автоматические тесты сигналов не заявляют поддержку аналогичного поведения Windows: там принудительные сигналы дочерним процессам имеют другую семантику.

## CI в GitHub Actions

Workflow `.github/workflows/ci.yml` запускается на каждый PR, push в `master` или `main` и вручную через Actions. Job `Quality` использует Ubuntu и Node.js 24, устанавливает зависимости через `npm ci`, затем выполняет lint, проверку типов, все тесты, сборку и `npm audit --audit-level=high` (включая dev-зависимости). Уязвимости high/critical блокируют успешное завершение CI.

Кешируется npm download cache, а не `node_modules`. Устаревшие запуски для того же PR или ref отменяются; таймаут job — 10 минут. OpenSSL уже доступен на Ubuntu runner. Реальная Jira и секреты не нужны: тесты используют локальный HTTPS mock. CI ничего не публикует.

Чтобы не допускать merge при упавшем CI, после первого запуска настрой GitHub **Settings → Rules → Rulesets** (или **Branches → Branch protection rules**) для основной ветки:

- запрети прямые изменения без PR и force push;
- потребуй успешный status check `Quality` из workflow `CI` и актуальность ветки перед merge;
- при наличии другого ревьюера потребуй минимум одно одобрение;
- проверь права обхода правил: обычные изменения не должны обходить проверки.

Эти настройки применяются на стороне GitHub, workflow сам их не включает. Для разбора сбоя используй лог первого упавшего шага и воспроизведи его локальной командой.

## Локальная проверка архива

```bash
npm pack
```

Команда собирает проект и создаёт `bluntjira-0.1.0.tgz`; публикацию она не выполняет. Тест `tests/package.test.ts` устанавливает созданный архив в чистый временный каталог и запускает установленный `bluntjira` через npm bin. Он проверяет MCP initialize, девять инструментов и `get_projects` через локальный HTTPS mock Jira.

В архив входят только LICENSE, README.md, package.json и шесть JS-файлов `dist`. Исходники, тесты, тестовые ключи, рабочие документы и конфигурации окружения туда не включаются.


## Изменения в проекте

Перед изменениями установи проект [из Git](../README.md#установка-из-git). Для проверки изменений выполни команды из начала этого документа. Описывай в PR, что изменилось и какие проверки выполнены; не добавляй настройки Jira, cookie, пароли или приватные ключи.
