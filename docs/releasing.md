# Подготовка релиза

Репозиторий: https://github.com/danillittle/bluntjira. Git содержит исходники, тесты, README, LICENSE, lockfile и конфигурацию сборки; локальные рабочие документы, отладочные скрипты, настройки Jira и собранные архивы исключены.

Перед первым релизом:

1. Выполни `npm ci` и `npm run check`. Для тестов нужен OpenSSL, как описано в [руководстве по разработке](development.md).
2. Проверь `git diff --cached` перед коммитом: там не должно быть реквизитов, локальных настроек или лишних файлов. Создай коммит и отправь его в GitHub.
3. Выполни `npm login --registry=https://registry.npmjs.org/`, затем проверь аккаунт через `npm whoami --registry=https://registry.npmjs.org/`. Не сохраняй токены в репозитории.
4. Проверь имя и версию: `npm view bluntjira name version --registry=https://registry.npmjs.org/`. Ответ E404 означает отсутствие доступного пакета, но не гарантирует право на имя.
5. Выполни `npm publish --dry-run`, проверь перечень файлов и метаданные. Эта команда не публикует пакет; `prepublishOnly` запускает lint, typecheck, тесты и сборку, а `prepack` собирает архив.
6. Только после проверки и решения о публикации выполни `npm publish`. Имя/версию опубликованного пакета нельзя использовать повторно; исправления выпускаются новой версией.
7. Проверь `npm view bluntjira@0.1.0 version` и вход через `npx -y bluntjira@0.1.0 login`, затем MCP initialize, tools/list и разрешённый вызов чтения через [конфигурацию MCP-клиента](../README.md#2-добавь-сервер-в-ai-приложение). Проверки записи требуют отдельного согласования.

Перед публикацией перенеси описание готовящейся версии в [CHANGELOG.md](../CHANGELOG.md) из раздела «Не выпущено» в раздел версии и укажи дату релиза. Для следующих релизов обновляй версию в `package.json`, lockfile, `src/index.ts`, примерах README и `index.html` согласованно. Не включай реальные Jira URL, cookie, пароли, npm-токены или тестовые приватные ключи в Git или архив.

## Автопубликация в npm

Workflow `.github/workflows/publish.yml` запускается при push тега `vX.Y.Z`, например `v0.1.1`. Обычный push в ветку пакет не публикует. Поддерживаются только стабильные версии: prerelease-теги отклоняются, публикация идёт с npm dist-tag `latest`.

Перед публикацией workflow проверяет:

- коммит тега входит в историю основной ветки репозитория;
- тег точно совпадает с версией `package.json`, версия согласована с обоими корневыми полями lockfile;
- lint, типы, все тесты (включая совпадение версии MCP с версией установленного пакета), сборка и security audit проходят;
- архив успешно создаётся и проходит `npm publish --dry-run`.

После этого отдельная job получает только подготовленный `.tgz` и публикует его без повторной сборки. `--ignore-scripts` на публикации архива не повторяет lifecycle scripts: все проверки и сборка уже выполнены в предыдущей job. Право `id-token: write` есть только у публикующей job, установка зависимостей выполняется без него. Долгоживущий `NPM_TOKEN` не используется.

### Одноразовая настройка npm

1. Убедись, что владеешь npm-пакетом `bluntjira`. Если пакета ещё нет, сначала выполни ручную первичную публикацию по инструкции выше: Trusted Publisher настраивается в Settings существующего пакета. Ответ E404 от registry не гарантирует доступность имени.
2. В npmjs.com открой **bluntjira → Settings → Trusted publishing**, добавь **GitHub Actions**:
   - Organization or user: `danillittle`;
   - Repository: `bluntjira`;
   - Workflow filename: `publish.yml` (без `.github/workflows/`);
   - Environment name: оставь пустым — workflow не использует GitHub environment;
   - если интерфейс предлагает Allowed actions, разреши прямой `npm publish`, а не только staged publishing.
3. Сохрани настройку и запланируй первый автоматический релиз в пределах срока её активации. По текущим правилам npm новая конфигурация истекает, если первая успешная публикация не выполнена в течение двух дней; истёкшую конфигурацию нужно создать заново.
4. Убедись, что GitHub Actions разрешены. Настрой ruleset для тегов `v*`: ограничь создание релизных тегов доверенными сопровождающими, запрети их изменение и удаление. Право отправить тег запускает реальную публикацию без дополнительного подтверждения.
5. После проверки OIDC-публикации рекомендуется включить в npm **Publishing access → Require two-factor authentication and disallow tokens** и отозвать ненужные токены.

Workflow использует GitHub-hosted Ubuntu runner, Node.js 24 и проверяет наличие npm >=11.5.1. При публикации через OIDC npm автоматически добавляет provenance для публичного пакета из публичного репозитория. Источник требований: [npm Trusted Publishers](https://docs.npmjs.com/trusted-publishers/).

### Выпуск следующей версии

Если `0.1.0` уже опубликована вручную, следующий автоматический релиз должен иметь новую версию, например `0.1.1`:

1. Обнови версию через `npm version 0.1.1 --no-git-tag-version` (обновляет `package.json` и lockfile без создания тега), затем согласуй `src/index.ts`, примеры README и `index.html`.
2. Выполни `npm run check` и `npm audit --audit-level=high`, закоммить изменения и отправь их в основную ветку через обычный PR-процесс. Убедись, что `publish.yml` уже находится в публикуемом коммите.
3. На нужном коммите основной ветки создай и отправь тег:

   ```bash
   git tag -a v0.1.1 -m "Release 0.1.1"
   git push origin v0.1.1
   ```

   **Внимание:** push этого тега запускает публикацию публичного пакета после успешных проверок. Используй новую, ещё не опубликованную версию.

4. Проверь workflow **Publish** в GitHub Actions и результат `npm view bluntjira@0.1.1 version`.

Если проверка или авторизация завершилась ошибкой до публикации, исправь причину и перезапусти workflow для того же неизменённого коммита, когда это применимо. Если нужно менять исходники или workflow, выпусти новый тег с новой версией, не передвигай существующий тег. Если пакет уже опубликован, повторный запуск не заменит его: npm запрещает повторное использование версии. Исправления выпускаются новой patch-версией; удаление тега не откатывает пакет в npm. При ошибочном релизе можно отдельно пометить версию deprecated и переключить `latest` на предыдущую исправную версию после проверки.
